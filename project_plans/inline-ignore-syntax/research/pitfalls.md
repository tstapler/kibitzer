# Pitfalls: inline ignore comments

Confidence: VERIFIED = code opened; INDUSTRY = general knowledge of linters (eslint-disable, noqa, nolint, clippy allow), not re-checked this session.

## Generic pitfalls (INDUSTRY)
- Gaming: agents blanket-ignore to turn a check green. Mitigations: required non-empty reason, per-rule (no bare "ignore all"), no file/block scope (already out of scope in requirements.md), a countable/greppable marker.
- Sprawl: ignores accumulate and are never revisited. Mitigation: unused-ignore report (open question 3 in requirements.md); the `fp` marker list doubles as a worklist.
- Stale ignores: the code is fixed or the rule is renamed and the comment lingers, silently. Needs an "unused ignore" finding, which requires knowing the pre-filter findings.
- Comment-in-string matching: a regex over raw text matches `"// kibitzer:ignore x -- y"` inside a string literal or Markdown code fence.

## Kibitzer-specific, with code evidence

1. Ordering with diff scoping (VERIFIED, low risk). In `src/check.rs` the native path scopes to changed lines first (`scope_output_to_changed_lines`, ~l.473-478), then calls `drop_accepted_findings` (~l.486) only on what survives. An ignore comment added in the same edit is in the post-edit file, so the filter sees it. The risk is the reverse: an ignore comment added on a line *outside* the edit's changed ranges for a finding *inside* them (e.g. comment above, finding line in range, comment line not) works fine, since the filter reads the whole file, not just changed lines. Stale/unused-ignore detection, however, cannot piggyback here: scoping has already discarded findings outside the edit, so "this ignore matches nothing" would be falsely reported for ignores on untouched lines. Compute unused-ignore only in an unscoped pass (`run`/LSP), or only for ignores whose target line is in `changed_lines`.

2. `compute_changed_lines` is substring-based (VERIFIED, `src/hook.rs:90-129`). It locates `new_string` via `match_indices`; if the edit only adds an ignore comment line, `new_string` is that edit text and ranges cover the comment line(s), not necessarily the flagged line. Pre-existing findings are scoped out anyway, so adding an ignore to an old finding is a no-op for output, fine. But a Write is unscoped (`hook.rs:94-96`), so every ignore is evaluated. Ambiguous `new_string` unions all occurrences (`hook.rs:114-118`), so an identical ignore comment pasted in several places widens scope harmlessly.

3. Line anchoring (VERIFIED). `filter_accepted` parses `{file}:{line}: {message}` and matches on exact `line_no` (`src/accepted_findings.rs:154-162`). An inline ignore on the "same or next line" needs a source read for every file, but today the read is skipped unless some accepted entry names the file (`accepted_findings.rs:141-146`); that early return must be reworked (cheap: one `read_to_string` already done by the checker, but not shared). Findings are not all anchored on the flagged statement: `over-commented` reports the first leading comment row, else decl start (`src/checkers/comment_quality.rs`, `check_proportionality` push, `line: leading_start_line.unwrap_or(...)`); `commented-out-code` reports per comment line (`comment_quality.rs:321-352`); cross-file duplicate reports `start + 1` (`duplicate_cross_file_checker.rs:262`). An "ignore applies to next line" rule will miss multi-line constructs; an ignore above `over-commented` would itself sit on the comment block it is meant to excuse.

4. Rule-id mismatch (VERIFIED). `extract_rule` falls back to the checker name when there is no `[rule-id]` prefix (`accepted_findings.rs:103-110`). So the ignore id for a prefix-less checker is the checker name (e.g. `primitive-obsession`) but for a prefixed one it is the rule (`flag-argument`, `verbose-comment`). Users cannot discover which from the message. Same ambiguity applies to a checker emitting several rules under one name; bracket prefix with a nested `]` truncates at the first `]` (`find(']')`). Doc must list the id explicitly and an unknown rule id in an ignore should be reported (otherwise silent no-op, which violates the "malformed -> clear error" scope item).

5. Ignore comment is itself checked by comment-quality (VERIFIED risk). `comment-quality-<lang>` walks every comment node (`comment_quality.rs:225-257`): `check_verbose_phrases` (l.296) lowercases the text and matches banned phrases, so a free-text reason like "this is simply a very important..." can trigger `verbose-comment`; `looks_like_code` (`:482`) could flag a reason containing `foo(bar)` or `x = y`; and the ignore comment adds to the over-commented line count (`check_proportionality` counts comment rows in the body and leading comments, `:643-700`; `MIN_COMMENT_LINES_FOR_RATIO`). Fix: skip comment nodes whose stripped text starts with `kibitzer:` in all three paths (and in `leading_comment_rows`/`collect_comment_rows` so they do not inflate the ratio). Also the markdown prose checks see `<!-- kibitzer:... -->` only if they read raw text; unverified.

6. HEAD baseline does not know about ignores (VERIFIED). `check_native_against_git_head` (`check.rs:~596-632`) re-runs the checker on `git show HEAD:<file>` and only consults `scope_output_to_changed_lines`, not accepted/inline filtering. Since it is evaluated only when the current result is non-passing after filtering, the effect is limited to downgrade logic, but an inline ignore present at HEAD is not applied when judging "predates your edits". Low impact, but be consistent: either filter the HEAD output too, or document it.

7. String-literal matching (UNVERIFIED for kibitzer, high likelihood). The only existing source scanning is line-based (`source.lines()`, `accepted_findings.rs:148`), with no tokenizer. A naive `line.contains("kibitzer:ignore")` would match string literals and Markdown fences, and test fixtures in kibitzer's own repo (checker tests embed Go/Rust source as string literals, e.g. `comment_quality.rs:909`). Safest: reuse the tree-sitter comment nodes (`comment_kinds`, `comment_quality.rs:173`) for code languages; for Markdown, restrict to HTML-comment nodes outside fenced code.

8. CRLF/tabs/whitespace (VERIFIED partially). `str::lines()` strips a trailing `\r` along with `\n`, so CRLF is safe for line-based scanning (`accepted_findings.rs:148`). But `compute_changed_lines` counts `'\n'` and matches `new_string` verbatim (`hook.rs:114-116`): an edit whose `new_string` uses `\n` against a CRLF file will fail to match, giving `None` (unscoped) - so ignores still apply, no worse than today. Tabs and varied spacing: the ignore parser must trim and accept `\t`; accepted-findings compares `trim()`ed content (`accepted_findings.rs:161-162`), the model to copy. Reason separator `--` vs em dash: the repo flags `em-dash-overuse` (`src/checkers/em_dash_overuse.rs`), so use ASCII `--`.

9. Path prefix coupling (VERIFIED). Both filters require `line.strip_prefix(format!("{}:", file_path.display()))` (`check.rs:~845`, `accepted_findings.rs:150-156`); any checker that prints a different path form (relative vs absolute) is silently unfilterable. Inline ignores inherit that fragility; no new risk but the same blind spot.

10. Gaming surface specific to kibitzer. The hook feeds findings to the agent immediately after an edit, so the cheapest response is to append an ignore comment in the next edit. That new edit itself fires the hook, and with a mandatory non-empty reason the agent can write any string. Consider (a) the `fp` marker count surfaced in hook output ("N inline ignores in this file"), (b) blocking-severity checks (`Severity::Blocking`, `check.rs:~496`) not being suppressible by inline comment, or requiring a distinct marker, (c) reporting ignores added in the current edit as advisory.

## Likelihood summary (kibitzer's code today)
- Likely/confirmed: rule-id ambiguity (4), comment-quality self-trigger (5), multi-line anchor mismatch (3), string-literal matching if line-based scanning is copied (7), early-return needing rework (3), unused-ignore blocked by scoping order (1).
- Unlikely/benign: CRLF (8), changed-lines interaction (2), HEAD baseline (6).
