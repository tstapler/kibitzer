# Research: Features / Prior Art for Inline Suppression

Confidence: prior-art syntax below is from the author's recall of each tool's documented behavior (INFERRED, not re-fetched this session; verify against current docs before citing in an ADR). Kibitzer codebase facts are VERIFIED by reading `src/accepted_findings.rs` and `src/checker.rs`.

## 1. Prior-art survey

| Tool | Syntax | Scope | Reason | Unused reporting | Rule matching |
|---|---|---|---|---|---|
| ESLint | `// eslint-disable-next-line rule -- reason`; `// eslint-disable-line`; `/* eslint-disable */ ... /* eslint-enable */` | next line, same line, block, file | optional after `--` (opt-in via `eslint-comments/require-description`) | `--report-unused-disable-directives` (warn/error) | comma-separated ids; bare form disables all rules |
| pylint | `# pylint: disable=id1,id2` (same line, or on its own line = rest of scope/block) | line, block to end of scope, file | none (free text after `#` allowed) | `useless-suppression` (I0021, off by default); `locally-disabled` info | symbolic name or numeric id; `all` allowed |
| flake8 / ruff | `# noqa: E501,W291`; bare `# noqa` | same line only (file-level `# flake8: noqa`) | none | ruff `RUF100` unused-noqa; flake8 has none | codes, prefix match (`E5`); bare = everything |
| golangci-lint | `//nolint:linter1,linter2 // reason` | same line, or a declaration/block if the directive sits above it | optional; `nolintlint` linter can require explanation and specific linter names | `nolintlint` flags unused (`allow-unused: false`) | linter names (not rule ids); bare `//nolint` flagged by nolintlint if `require-specific` |
| clippy / rustc | `#[allow(clippy::lint)]`, `#[expect(lint, reason = "...")]` | attribute scope (item/block/crate) | `reason =` supported (stable 1.81); `clippy::allow_attributes_without_reason` lint | `#[expect]` warns when the lint does not fire (`unfulfilled_lint_expectations`) | full lint path |
| RuboCop | `# rubocop:disable Cop/Name` ... `# rubocop:enable Cop/Name`; trailing same-line form | same line, or range between disable/enable | none | `Lint/RedundantCopDisableDirective` | cop name or department (`Metrics`); `all` |
| Semgrep | `// nosemgrep: rule-id` (or bare `nosemgrep`) on flagged line or the line above | same line / previous line | none (free text) | none built in | rule id, can be listed; bare matches all |
| SonarQube | `// NOSONAR` (all rules on line); newer `// NOSONAR(rule1,rule2)` in some analyzers | same line | none | none | bare is catch-all, widely criticized as too broad |
| Vale | `<!-- vale Style.Rule = NO -->` ... `<!-- vale Style.Rule = YES -->`; `<!-- vale off/on -->`; also `<!-- vale Style.Rule = NO -->` pairs in Markdown, `# vale off` in comments for other formats | range between off/on | none | none | Style.Rule name; `off` = all |
| mypy / pyright | `# type: ignore[code]`, `# pyright: ignore[rule]` | same line | none | `--warn-unused-ignores`, `reportUnnecessaryTypeIgnoreComment` | bracketed codes |

### Cross-tool patterns worth copying
- **Same-line + next-line is the dominant pair** (ESLint, Semgrep, golangci in practice). Same-line-only (noqa, NOSONAR) forces trailing comments that break formatters and line-length limits; next-line-only forces extra lines. Offering both is the proven convention.
- **Explicit rule ids beat bare "ignore all"**. Every tool that allows a bare form has a companion lint to forbid it (`nolintlint`, `eslint-comments/no-unlimited-disable`, `blanket-noqa` in ruff). Kibitzer's requirement of rule + reason should make bare forms a hard error.
- **Reasons**: ESLint's `-- reason` and Rust's `reason = "..."` are the cleanest. Both are optional in the tools themselves; kibitzer making it mandatory is stricter than all prior art, which is consistent with `accepted/`.
- **Unused-suppression reporting** is the mature-tool feature that keeps ignores from rotting: ESLint, ruff RUF100, rubocop Redundant, rustc `expect`, mypy. Almost universally off by default because it is noisy across tool upgrades. Kibitzer has an advantage: it controls the checker, so "unused" is exactly decidable (the ignore matched no finding in this run).
- **Block ranges** (`disable`/`enable`) are the main source of "forgot to re-enable" bugs (rubocop, vale, eslint). Requirements already put block/file ignores out of scope; prior art supports that (line-scoped covers most of the usage; ranges are what get abused).
- **Marker distinguishing misfire from accepted tradeoff** has no direct precedent in the tools above. Closest analogs: Sonar's "False Positive" vs "Won't Fix" resolution states (UI-based), and Semgrep's triage states. So `fp` tag / separate marker is novel; keep it a cheap optional attribute.

## 2. Kibitzer-specific facts (VERIFIED)

- `Finding` is `{ line: usize, message: String }` (`src/checker.rs:12-15`): one line, no end line, no file. A multi-line construct has a single reported line, so the ignore only needs to match that one reported line (or the line above it).
- `filter_accepted` (`src/accepted_findings.rs:131`) operates on the *rendered text* (`<path>:<line>: <message>`), parsing the line number and `extract_rule(message, checker_name)` (the `[rule-id]` prefix, else checker name). An inline-ignore filter slots in the same way: parse each output line, look at source lines `line` and `line-1`.
- It already short-circuits file reads when no entry names the file. The inline version cannot use that shortcut (any file may carry a comment) but can reuse the source text the checker already read, or do a cheap `memchr`-style scan for the marker substring `kibitzer:` before parsing; this protects the "no measurable slowdown" NFR.
- `src/god_class.rs:520` emits `line: 0` (verified by grep); other checkers may report file-level findings on line 1 or 0.

## 3. Edge cases for kibitzer

1. **Multi-line findings.** Checker reports the start line (function signature, first line of a duplicate block). Ignore goes on that line or directly above it. Decorators/attributes/doc comments between the comment and the function (Rust `#[derive]`, Python `@decorator`, Java annotations, Go doc comment) make "line above" ambiguous. Options: (a) strictly the physical previous line; (b) skip over contiguous comment lines and attribute lines. Recommend (a) plus documenting that the finding line is what counts; printing the finding line number in the message makes this unambiguous. Another wrinkle: when the checker's reported line is a decorator vs. the `def`, placement differs per language; the reported-line rule keeps it mechanical.
2. **Cross-file `duplicate-code-cross-file`.** Finding is reported at one location but names the other. Decision needed: honor an ignore at the reported location only (simple, deterministic), or at either side. Honoring either side requires the filter to read a second file and breaks the "single pass over already-read text" NFR. Recommend reported-location-only, and have the message name which file/line carries the ignore. Check whether the finding is emitted once per file (both sides) or once overall; if per side, each side needs its own ignore, which should be documented.
3. **Markdown HTML comments.** `<!-- kibitzer:ignore rule -- reason -->` is invisible when rendered, which is desirable. But: (a) inside fenced code blocks it is literal text and must not count (or should it, for docs that show the syntax? it must not, or `docs/suppressing-checks.md` itself would suppress things); (b) prose checks report a paragraph-start line, so the comment must sit on the line above the paragraph, which in Markdown means a blank-line-adjacent HTML block that could itself split a paragraph or break list continuation; (c) `markdown-link-integrity` reports link lines inside tables/lists where a leading comment line is awkward; same-line trailing `<!-- ... -->` is the safer form there; (d) markdown prose checks (`repetitive-sentence-structure`, `missing-paragraph-break`) analyze text, so the comment itself should be excluded from the prose they measure, or it will add a sentence/"paragraph" and can create new findings.
4. **Checkers reporting line 0 / file-level** (`god_class.rs:520`; likely `file-complexity`, `file-size`). No line to anchor to. Options: ignore the comment at line 1 (top of file) for any finding on line 0/1; or make file-level findings unsuppressible inline and point to `accepted/`/`inspect.json`. Recommend: treat an ignore in the first N lines (line 1) as covering line-0 findings, because file-level is exactly the case where "ignore near the top of the file" is natural. Must be defined, not left implicit.
5. **Comment-in-string false matches.** A string literal containing `kibitzer:ignore` (test fixtures, docs for kibitzer itself, this repo's own sources) would suppress findings. Mitigations: require the marker to start at a comment token (`//`, `#`, `--`, `/*`, `<!--`) with only whitespace before the comment on the line or code before it; ideally use tree-sitter comment nodes where a grammar exists (kibitzer already parses with tree-sitter for several languages) and fall back to a lexical comment-prefix match for languages without one. Kibitzer's own source/tests will contain the marker text in string literals, so this is directly testable on the repo itself.
6. **Interaction with `comment-quality-*`.** An ignore comment is a comment: `commented-out-code` could fire on `kibitzer:ignore foo -- reason` (looks like `ident: ident ...`), `verbose-comment` on long reasons, `over-commented` on density. The ignore comment must be exempted from comment-quality classification (strip it before analysis), or the ignore would manufacture new findings. Also, can `comment-quality` rules themselves be ignored inline? Yes, and that should work uniformly, but the exemption means the ignore comment is never itself flagged, so it cannot ignore itself. Also check `syntax-rules` comment/`todo`-style rules and `ai-vocabulary`/prose checks that might scan comment text in code files.
7. **Interaction with `.kibitzer/accepted/`.** Both mechanisms can match the same finding. Either order produces "suppressed"; the observable difference is only in unused reporting (an ignore that is shadowed by an accepted entry looks unused if accepted runs first). Define precedence: run inline first (cheapest, no config lookup), accepted second, or run both and mark an ignore used if it matches regardless. Also: `accepted/` stays authoritative for non-comment-able locations (JSON files, generated code, line-0 findings), so docs should position inline as the default and accepted as the fallback.
8. **Rule-id matching.** `extract_rule` gives the `[rule-id]` bracket prefix or the checker name. Single-rule checkers (primitive-obsession, duplicate-code, file-complexity, go-*) use the checker name. Ignore comments must use that same identifier so the two mechanisms agree. Open question: allow checker-name as a wildcard for all of its rules (like rubocop departments)? Cheap and useful (`syntax-rules-go`), but weakens "name the rule". Prefer rule id only at first; or accept both with an exact-match preference.
9. **Multiple rules on one line / multiple ignores for one finding line.** ESLint and golangci allow comma lists. Support `rule1,rule2` to avoid stacking comment lines, each with its own reason being awkward: one reason per comment, multiple rules share it.
10. **Language comment-syntax detection.** Derive the comment prefixes from `checker::Language` / file extension; for non-tree-sitter text files (Markdown, shell, YAML, TOML) use a small prefix table. Python `#` vs Go `//` vs Rust `//` vs Java `//` vs Markdown `<!-- -->`. Block comments `/* ... */` single-line should also work in C-family files.
11. **Windows line endings / tabs / trailing whitespace** in the comment; trim the reason.
12. **Daemon/LSP incremental runs.** The ignore comment edit changes only the comment line; findings are cached by checker. Make sure cache invalidation keys on file content (any edit invalidates), which is naturally true if the filter is applied after the checker result and not cached before it. LSP additionally should surface a diagnostic on the malformed/unused ignore at the comment's own line.
13. **`kibitzer check backtest` / corpus runs.** Suppressed findings should still be countable (a `--show-suppressed`/`--no-ignores` mode) so backtests and triage scripts see raw checker output; otherwise ignores in the repo corpus hide the false-positive rate you are trying to measure. The existing `FilterOutcome.dropped_any` shows the pattern for reporting that something was dropped.

## 4. Unstated needs

- **Agent discoverability of the syntax (high value).** Agents see the finding message, not the docs. Each finding line should carry a copy-pasteable ignore hint, e.g. `... (to dismiss: // kibitzer:ignore flag-argument -- <reason>)`, with the language's correct comment prefix and the exact rule id (the id agents most often get wrong, since checker name vs rule id differ). Cost: tokens on every finding. Mitigation: print the hint once per run/file footer ("To dismiss a finding: add `<prefix> kibitzer:ignore <rule> -- <reason>` on or above its line") rather than per finding, or only in the hook/MCP path (agents) and not in `kibitzer run` human output. This also needs a guard against agents reflexively silencing real findings: the hint should say "if this is a checker misfire or a deliberate tradeoff", and the mandatory reason plus a visible diff provide the audit trail.
- **Prefer agents flag misfires, not just hide them.** The `fp` tag (or separate marker) is what produces the maintainer worklist; the hint should offer both forms and state when to use each ("checker is wrong" vs "correct but intentional").
- **Unused/stale ignore reporting** is needed because the whole point of line-anchored ignores is that they survive edits; the corollary is they also survive the code being fixed, leaving dead ignores. Prior art says report it, off-by-default or as a low-severity finding. Kibitzer can report exactly. Suggest: an `unused-ignore` finding on the comment line, on by default only in `kibitzer run`/CI mode and not in the PostToolUse hook (avoid feeding agents noise from other checks running on partial scope; also `scope_output_to_changed_lines`/diff scoping may mean the finding was not evaluated at all, which would wrongly look "unused").
- **Diff-aware scoping interaction.** kibitzer is "diff-aware" (`check::scope_output_to_changed_lines`): if only changed lines are checked, an ignore for an unchanged, un-evaluated line has nothing to match. Unused reporting must only consider ignores whose target line was in scope, or it will produce false "unused" reports in hook mode.
- **Malformed ignore as a visible finding** (requirements already ask for this): include missing rule, missing/empty reason, unknown rule id (typo; compare against the registered rule list so `flag-arguement` does not silently do nothing), and bare `kibitzer:ignore`. Unknown-rule detection is the highest-value one because a typo otherwise looks like a no-op.
- **Greppability / stable marker.** A single fixed token (`kibitzer:ignore`, `kibitzer:false-positive` or `fp`) so `rg 'kibitzer:'` lists everything; matches the "cheap greppable signal" success metric. Provide `kibitzer check false-positives` (or similar) to list ignores tagged as misfires, with file:line, rule, reason, and ideally the flagged source line so maintainers can paste into a test.
- **Security/abuse consideration.** An agent could blanket-ignore findings to make the hook go quiet. Mandatory reasons and diff visibility are the mitigation in the requirements; consider a per-run summary count ("3 findings suppressed inline") so suppression volume is visible in hook output, mirroring `dropped_any`.
- **ADR needed**: reversing the "no inline suppression comment" stance in `docs/suppressing-checks.md` / `docs/accepting-findings.md` (already flagged in requirements).

## 5. Suggested defaults (for the architecture phase to confirm)

- Syntax: `<comment-prefix> kibitzer:ignore <rule>[,<rule>...] -- <reason>`; misfire form `kibitzer:ignore <rule> fp -- <reason>` or distinct `kibitzer:false-positive`; choose one in ADR.
- Scope: same line or the immediately preceding line (physical); line 1 also covers line-0/file-level findings.
- Mandatory non-empty reason; unknown rule and missing parts are reported findings.
- Unused ignores reported as a finding in CI/`run` mode, off in the hook path.
- Ignore comments excluded from comment-quality and prose analysis; marker only recognized in real comment tokens.
- Cross-file duplicates: ignore at the reported location only.
