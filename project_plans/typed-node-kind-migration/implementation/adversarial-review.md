# Adversarial Review: typed-node-kind-migration

**Date**: 2026-09-22
**Verdict**: CONCERNS

## Blockers

- [ ] **No mechanical completeness check anywhere in the plan.** Success Metrics (requirements.md) require *every* named-concrete-kind comparison in the 23 scoped files to be migrated. Every story's acceptance criteria enumerate specific line numbers/counts by hand (e.g. "20 comparisons," "the 11 comparisons"), but nothing verifies after the fact that no comparison was missed — the backtest-corpus re-run only proves *behavior is unchanged for the code paths the corpus happens to exercise*, not that *every* `.kind() ==` site in the file was actually converted. A worker who converts 17 of 20 sites in a file, none of which the backtest corpus happens to trip, produces a story that passes every stated AC while leaving latent typo risk — the exact failure mode this migration exists to close. Phase 4's completion story (4.1.1) re-runs backtests and narrows the `#![allow(...)]`, but that allow only flags unused *enum variants*, not leftover raw-string comparisons. — **Recommendation**: add a mechanical grep/ast-grep sweep as a Phase 4 task (e.g. `rg '\.kind\(\)\s*(==|!=)|match\s+\S+\.kind\(\)' src/` filtered against the known seam-comment list) and require zero unexplained hits before the migration is declared complete.

- [ ] **No "stop and don't merge" gate when a backtest diff is non-empty.** Every story's backtest AC is phrased as Given/When/Then assuming success ("finding counts match exactly"); the plan never states what a worker or reviewer does when they don't match. Risk Control's only failure-handling text is post-merge (`git revert` the commit). requirements.md's own Feasibility Risks section names this as the central risk ("a wrong mapping introduced during the migration is invisible in exactly the same way... Mitigation: mandatory backtest-corpus re-run"), but the plan operationalizes the mitigation as a check with no documented "fail" branch. Under time pressure, a worker with a non-empty diff has no written protocol beyond "figure it out" — increasing the odds a real regression gets rationalized and merged rather than blocked. — **Recommendation**: add one line to Risk Control (or to each story's AC template): "A non-empty backtest diff blocks merge for that story; do not proceed to seam-comment/cleanup tasks or mark the story done until the diff is resolved or the finding is confirmed as a pre-existing flake unrelated to this migration."

## Concerns

- [ ] **ADR-001's "9 sites" count is stale relative to the plan's own enumeration.** ADR-001 and the plan's Domain Glossary (plan.md:20) both state "Exactly 9 sites exist (6 in rules.rs, 3 in symbol_extract.rs)." But Story 3.1.2's actual seam list for `rules.rs` alone is 8 items: the 6 named engine functions, plus `collect_identifiers`'s L899 site ("added to the seam list" per Story 3.1.1's AC, plan.md:365), plus the `rules.rs:784` `.contains("comment")` substring check (plan.md:390-395) — both of which are absent from ADR-001's/the glossary's "6 in rules.rs" tally. That's 8 + 3 = 11 real seamed sites, not 9. The technical treatment is internally consistent (both extra sites are correctly identified and seamed in Story 3.1.2), but the summary count that ADR-001 exists to document is now wrong, which will mislead whoever reads the ADR later without cross-checking the plan line-by-line. — **Recommendation**: update ADR-001's Context/Decision/Consequences sections (and the glossary row) to state 11, or split the count explicitly as "6 config-driven engine functions + 1 substring check + 1 generically-called helper = 8 in rules.rs, 3 in symbol_extract.rs."

- [ ] **No enforced ordering for the `rules.rs`/`symbol_extract.rs` two-story sequences.** The dependency diagram correctly shows `3.1.1 ─► 3.1.2` and `3.2.1 ─► 3.2.2` as sequential (not a hidden gap — the plan does acknowledge it), but that ordering exists only as documentation in a markdown diagram. Nothing in the plan describes a mechanism (task-tool dependency, file lock, or explicit "do not dispatch 3.1.2 until 3.1.1 has merged" instruction to the SDD implementation coordinator) that prevents two parallel workers from being handed both stories at once, which would produce two conflicting diffs against the same file. — **Recommendation**: state explicitly in Phase 3's intro (or in Story 3.1.2/3.2.2's AC) that these are gated stories, not just documented as sequential in the diagram, and that the implementation coordinator must serialize them.

- [ ] **Idiom-consistency across ~7 independently-run Phase 2 stories relies on convention, not a check.** The "worker's choice" of codemod-or-hand-edit (Pattern Decisions table, plan.md:36) is only anchored by Story 1.1.2's single reference file (`go_ignored_error.rs`) and a Risk Control note to land Phase 1 before parallelizing Phase 2. Nothing verifies that the ~7 parallel Phase 2 stories actually converged on the same `Kind::of(node) == Kind::Variant` / `matches!` idiom rather than, say, one worker using `Kind::from_kind_str` inconsistently or a different multi-arm style that happens to also pass clippy. `cargo clippy -D warnings` catches some drift (e.g. `match_like_matches_macro`) but not stylistic inconsistency in general. — **Recommendation**: add a lightweight idiom-consistency check to Phase 4 (e.g. a quick `rg 'Kind::of\(' -A1` skim across all touched files, or a five-minute manual pass) before the completion signal, or explicitly accept this as a known, low-cost residual risk given the small blast radius of a style-only inconsistency.

- [ ] **requirements.md's own file count is inconsistent with the plan's (self-acknowledged) file count.** requirements.md's scope grep block actually lists 23 files, not "~22" as stated in both requirements.md's Problem Statement/Appetite and the task prompt framing this review. The plan itself is aware of this — Story 2.3.1 explicitly says it exists "only so the file-count/commit-count reconciles against the full 23-file scope list" — but requirements.md was never corrected to say 23, leaving a live discrepancy between the two documents a future reader would have to notice and reconcile themselves. — **Recommendation**: fix requirements.md's "~22 files" language to "23 files" (or explain the discrepancy inline) rather than relying on a buried aside in Story 2.3.1 to self-correct it.

## Minors

- Domain Glossary's "Mechanical comparison... The majority case (18 of 22 files)" (plan.md:19) uses yet a third file count (18) distinct from both "~22" and the reconciled 23 — worth a single consistency pass across the whole document once the above file-count fix lands.
- Story 3.3.1's AC for the inline test assertion at `import_graph.rs:2229` says "(or the equivalent KotlinKind/whichever grammar that test targets — confirm from context)" — this is a plan gap (the story doesn't actually know which grammar the test is for) rather than a real risk, since the task is a 2-minute lookup, but it's a sign this specific site wasn't fully researched before planning.
- No story addresses what happens if `ast-grep`/`sg` isn't installed in a given worker's environment when they choose the codemod path — low risk since hand-editing is always the documented fallback, but worth a one-line note.
