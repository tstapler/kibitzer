## Concerns

- **Story 3.1.2 / Story 3.2.2 — seam isolation is comment-only, not structural** — The plan's own "Isolate via seam" pattern decision (per `code-architecture-best-practices`) calls for wrapping legacy behavior behind a visible boundary (adapter/facade/anti-corruption layer); the plan implements this as a one-line comment above each of the 6 `rules.rs` engine functions and 3 `symbol_extract.rs` functions, not a structural grouping. A reader scanning the file's symbol outline (or an IDE minimap) has no visual cue that these specific functions are the deliberately-untyped seam — only a reader who opens each function body and reads the comment learns that. Since Option A (generic trait) is correctly ruled out as new abstraction infra, a full facade isn't available here, but a cheaper structural cue is: group the seamed items under a clearly named boundary (e.g., a `// ==== SEAM: cross-grammar raw-string engine (ADR-001) ====` banner delimiting a contiguous block, or physically relocating the 6 `rules.rs` functions into a `mod raw_kind_engine { ... }` submodule within the file) so the boundary is structural, not just prose a reader can skip. **Remediation**: add this as an explicit task under Story 3.1.2/3.2.2 rather than "add seam comments above each function" as currently written.

- **Tech Debt Disposition row 3 (`complexity.rs`) — pre-existing cross-checker coupling left unremarked** — Verified via `grep`: `rules.rs:487` defines `pub(crate) fn lang_config(...)`, and `complexity.rs:104,128` are the only cross-file callers of `.function_kinds` (`crate::checkers::rules::lang_config(Language::Go).function_kinds`). This means one checker file (`complexity.rs`) already reaches into another checker file's (`rules.rs`) internal config accessor — a layering smell independent of this migration's typing question. The plan's disposition table correctly declines to migrate these 2 sites (consistent with the zero-behavior-change constraint) but doesn't note that the *coupling itself* is worth flagging for a future cleanup, separate from the kind-typing decision. **Remediation**: add one sentence to that table row: "this cross-checker reach-into (`complexity.rs` → `rules.rs::lang_config`) is pre-existing and out of scope to fix here, but is a layering smell worth a tracked follow-up independent of kind-typing."

- **plan.md doesn't carry forward `research/stack.md`'s field-name-string caveat** — `research/stack.md` explicitly and correctly documents that `Node::child_by_field_name(&str)` field-name strings (`"type"`, `"function"`, `"operand"`, `"left"`, etc.) have **no typed equivalent** in `node_kind.rs`/`build.rs` and remain primitive-obsessed forever, distinct from the `.kind()` comparisons this migration fixes. Grepped `plan.md` for `field_name`/`FieldId` — zero hits. Since `plan.md` (not `research/stack.md`) is the artifact Phase 2/3 workers actually execute from, a worker who only reads the plan has no way to know this residual gap exists, and might reasonably wonder why a field-type comparison like `ty.kind() != "type_identifier"` gets migrated while the field-name string `"type"` in `child_by_field_name("type")` two lines away does not. **Remediation**: add a short bullet to plan.md's Domain Glossary or Unresolved Questions: "`child_by_field_name` field-name strings are a distinct, unrelated mechanism with no typed equivalent — they remain raw strings permanently; see research/stack.md."

- **No mechanical check for migration completeness/idiom convergence beyond backtest-count matching (Lens: pattern selection)** — Every story's correctness gate is "backtest finding counts match baseline." That catches a *wrong* enum mapping (the failure mode this migration targets) but not a *missed* comparison — if a worker simply overlooks one `.kind() == "..."` site, finding counts still match (nothing about that site's behavior changed), and nothing in the plan's ACs would catch the omission unless the specific missed line happens to matter to a backtest fixture. Given kibitzer already dogfoods itself (`.claude/inspect.json`'s `architecture_assessment`/native checks run against this repo), a cheap addition — e.g., `grep -n '\.kind()\s*[!=]=' <file>` per touched file, cross-checked that every remaining hit sits adjacent to a `// Seam:` comment — would mechanically confirm each story actually finished, rather than relying solely on manual diff review. **Remediation**: add this grep-and-assert step as a task in each Phase 2/3 story's CI-gate task (or once, as a Phase 4 completion-signal check across all 22 files).

- **Pattern Decisions table's citation for the 9 seam sites blurs a real research override** — The table cites "ADR-001 / architecture.md §3" as the source for choosing Option (C) "leave unmigrated" for all 9 cross-grammar sites. But `architecture.md` §3 ("Recommendation for Phase 3") explicitly recommends **(B) duplicate-per-language** for 8 of those 9 sites (the 6 `rules.rs` engine functions + `symbol_extract.rs`'s 2 `LangRuleConfig`/`LangSymbolConfig`-driven sites), and (C) only for `callee_text_for` specifically. ADR-001 itself is transparent about this override ("(B) ... Rejected for this migration (recommended as a possible future ... follow-up)"), but plan.md's Pattern Decisions table citation reads as if architecture.md's research supported (C) uniformly across all 9, which it did not. This is a citation-accuracy issue (a rationale needs an accurate source), not a wrong decision — ADR-001's own reasoning for overriding (B) is sound. **Remediation**: reword the Source cell to "ADR-001 (deliberately overriding architecture.md §3's per-site B/C recommendation)" so the citation doesn't imply uniform research agreement.

## Nitpicks
- `<Lang>Kind::Other`'s dual semantics (anonymous/punctuation token *and* synthetic `ERROR`/`MISSING` node, per the Domain Glossary) is correctly never targeted by any migrated comparison, but the plan doesn't flag it as a candidate future improvement to `node_kind.rs` itself (out of this migration's scope, since that file is explicitly untouched infra) — worth a one-line mention in Unresolved Questions for whoever eventually revisits `node_kind.rs`, not a gap in this migration.
- Pattern Decisions table's "worker's choice: codemod-assisted OR hand-edit" framing treats both options as equally likely per story, which slightly under-commits relative to `research/build-vs-buy.md` §4's recommendation to use the codemod as the *default* approach for the ~16-18 mechanical files specifically to capture its verified time savings on ~140 repetitive comparisons. Non-blocking — correctness is identical either way since the backtest gate applies regardless of which path a worker takes.
- Verified as **not** an issue on inspection (Lens: testability of the two-step seam disposition): Stories 3.1.1→3.1.2 and 3.2.1→3.2.2 each independently require full `cargo build`/`cargo test`/backtest passage in their own ACs, so the file is never left in a broken or partially-testable state between the "migrate mechanical majority" and "add seam comments" steps — the second step is a comment-only diff. No remediation needed; noting this since the review brief specifically asked to check it.
