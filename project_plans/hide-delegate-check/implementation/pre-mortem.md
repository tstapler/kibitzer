# Pre-mortem: hide-delegate-check
**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Phase 6 (backtest/validation) runs dead last, after all 61 tasks across 6 languages, tests, and docs are already implemented — so if the corpus FP rate is unacceptable, the "narrowing v1 scope" fallback in Risk Control means discarding already-built per-language work rather than a cheap early course-correct. `pitfalls.md §5` itself budgets a suppression-heuristic revision as "near-certain," meaning this isn't a hypothetical — the plan already expects to be wrong, just not until the very end. | Phase 6.2 triage (Task 6.2.1c) shows a high false-positive rate (e.g. most findings on `apache/cassandra`'s builder-heavy code or `servo/servo`'s iterator chains are confirmed FPs) only after Phases 1-5 are fully merged/implemented on the feature branch, with 7 languages' worth of node-kind wiring, allowlists, and 14+ unit tests already locked in around the current design. | Add a cheap smoke-test checkpoint after Phase 1 + one language (e.g. wire only Rust or Go, run `kibitzer run` against one corpus repo) *before* doing the remaining 5 languages' Epic 2.x work, so the core walk/threshold/suppression design is validated against real code early, not only at Phase 6. | P1 |
| 2 | kibitzer's own source (`src/rules.rs`) is never included in the Phase 6 backtest corpus (`docs/backtest-repos.md`'s list is `kubernetes/kubernetes`, `apache/cassandra`, `servo/servo`, `BurntSushi/ripgrep`, `denoland/deno`, `microsoft/vscode`, `stapler-squad` — kibitzer itself is absent), yet it's a Rust codebase whose own `rules.rs` is full of `node.child_by_field_name("x")?.kind()`/`.utf8_text(src).unwrap_or("")`-style Option/Result chains that the adversarial review already confirmed `RUST_FLUENT_ALLOWLIST` doesn't cover. Because `hide-delegate` ships in `default_checks()` with no opt-in, kibitzer's own dogfooding CI/PR-review flow will start surfacing `[hide-delegate]` findings on its own newly-added and future code the moment this merges. | The very PR that lands `hide-delegate` (or the next PR touching `src/rules.rs`) gets flagged by its own new check during kibitzer's self-review step, and reviewers have to manually dismiss it as a known gap instead of the corpus backtest having caught it pre-merge. | Add kibitzer's own repo as an explicit Phase 6 backtest target (`kibitzer run .` from within the kibitzer checkout itself), not just the 7 external corpus repos — it's the one codebase guaranteed to be scanned by this check on literally every future PR. | P2 |
| 3 | Because kibitzer's stated primary consumer is an AI coding agent acting on findings inline (not a human reading a dashboard), an agent responding to a `[hide-delegate]` finding can satisfy the linter without fixing the underlying coupling: split a 3-hop chain into two 2-hop chains across a new trivial delegating method/wrapper (e.g. `a.GetB().SomeNewHelperOnB()` where the helper's body is `b.GetC().DoThing()`). Each site is now individually under `MAX_CHAIN_LINKS`, so no finding fires anywhere, even though the same object graph is still being reached through — the Law of Demeter violation is relocated, not resolved. Unlike a human reviewer, an agent optimizing against a lint signal has no built-in skepticism about whether the "fix" it just applied addresses the check's actual intent. | Diffs (visible in transcript backtests once the check is live) show agents adding new one-line delegating methods/wrappers whose only purpose is to shorten the caller's chain, not to expose new behavior — a rise in speculative-generality methods correlated with `[hide-delegate]` findings in prior turns of the same session. | Phase 6.1's transcript backtest (Task 6.1.1a) should explicitly search transcripts for this "relocate, not resolve" response pattern as its own triage category, not just "did it fire correctly" — and the finding message itself should note that a valid fix exposes new behavior on the base type, not merely forwards the chain one level down. | P2 |
| 4 | The three non-empty `fluent_allowlist` consts (TS/JS, Java, Kotlin, plus Rust's already-flagged gap) are static data with no defined update owner or re-validation cadence. Unlike every other `rules.rs` rule (all purely structural — nesting depth, line counts, parameter counts), `hide-delegate`'s accuracy depends on a semantic vocabulary (stdlib method names) that changes as languages/ecosystems evolve (new Rust iterator adapters, new Java Stream methods, new JS Array methods) — and nothing in the plan schedules a future backtest re-run to catch staleness; Phase 6 is framed as a one-time pre-merge gate, not a recurring one. | Months after shipping, a language ecosystem update or a corpus repo bump introduces new idiomatic fluent-method names the allowlist doesn't know about, and `[hide-delegate]`'s false-positive rate creeps upward with no automated or scheduled signal — only a user complaint would surface it. | Document an explicit re-triage trigger (e.g., "re-run Phase 6's corpus backtest when `docs/backtest-repos.md`'s corpus is refreshed, or at least annually") and name an owner/location for allowlist updates in `docs/hide-delegate-false-positives.md`, rather than leaving the allowlists as a one-time snapshot. | P2 |
| 5 | `MAX_CHAIN_LINKS = 2` is chosen purely by shape-analogy to `MAX_NESTING_DEPTH`/`LONG_FUNCTION_LINES` (Pattern Decisions table), with zero data-driven calibration against real dot-chain density — unlike, e.g., `comment-quality`'s hand-labeled corpus. Dot-chain depth and block-nesting depth are dimensionally different metrics (idiomatic code routinely has 3+ hop chains — `req.Header.Get("X").TrimSpace()`, `resp.Body.Close()` callers, config-getter chains — that aren't Demeter violations), so there's no evidence the boundary belongs at 3 rather than 4. Worse, Phase 4's 14 per-language unit tests (2 per language) hard-assert the current boundary as correct behavior ("3 hops must flag"), so if Phase 6 shows the threshold itself is miscalibrated, fixing it means revisiting tests across all 7 languages, not just tweaking one const. | Phase 6.2 triage shows a disproportionate share of confirmed false positives sitting exactly at hop-count 3 (the boundary), across multiple corpus repos/languages, suggesting the threshold — not just the allowlist — is the actual miscalibration, but Phase 4's already-landed tests assert 3-hop chains must flag, creating rework friction to raise it. | Before Phase 4 locks test fixtures to the exact boundary value, spot-check hop-count distribution on 1-2 corpus repos (a simple `grep`/AST count, not a full backtest) to sanity-check `MAX_CHAIN_LINKS = 2` against real code density; alternatively, frame `MAX_CHAIN_LINKS` explicitly as "provisional pending Phase 6" in test doc comments so raising it later isn't treated as breaking a locked contract. | P1 |
