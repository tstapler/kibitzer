# Validation Plan: type-hierarchy-graph

**Date**: 2026-09-22

## Happy Path Scenario
Given the Baseline (`ArchModel` has `packages`/`import_edges`/`call_edges`/`field_accesses` but no type-to-type edge, and `symbol_extract.rs` already parses `Type`/`Interface` declarations for Go/TS/Tsx/JS/Java/Kotlin), when `build_model` runs on a repo containing a Go struct that embeds another struct in the same package, then `ArchModel.type_edges` contains a resolved `TypeRelationEdge { kind: Some(Extends), resolved: true }` connecting the two `SymbolNode::id`s, and that edge is retrievable end-to-end via the `list_supertypes` MCP tool. *(Go embedding is the plan's "easy/required v1 case" — Pattern Decisions table — so it anchors the pipeline: extraction → resolution → MCP traversal.)*

## Test Stack
- **Unit**: Rust, built-in `#[test]` + `cargo test`, colocated `#[cfg(test)] mod tests` blocks in each source file (`src/arch_model.rs:853`, `src/symbol_extract.rs:1039`, `src/mcp.rs:1121`, `src/arch_export.rs:96`) — this codebase's existing convention (no separate assertion-library crate; std `assert!`/`assert_eq!`). Language-fixture tests build source strings, parse with tree-sitter, and assert on extracted `RawTypeRelationSite`/`TypeRelationEdge` values, mirroring `symbol_extract.rs`'s existing per-language test pattern.
- **Integration**: Same `#[cfg(test)]` mechanism, no separate `tests/`-directory crate for this feature (the repo's `tests/` dir holds unrelated CLI/hook/plugin contract tests) — "integration" here means a test that exercises the full pipeline across layers (multi-file `build_model` runs end-to-end through extraction+resolution, or a simulated MCP tool call through request parsing → traversal → pagination → response serialization) rather than a single function in isolation. No external service, database, or network dependency exists in this feature, so no test-double/mocking framework is needed.
- **E2E / UX**: N/A.
