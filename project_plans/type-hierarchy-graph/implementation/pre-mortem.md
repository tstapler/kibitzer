# Pre-mortem: type-hierarchy-graph
**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | `type_edges` ships with a silent extraction/resolution bug (e.g. a Kotlin `kind_hint: None` site or an ambiguous cross-package Go embed resolved wrong) that no one notices, because the only consumers per `requirements.md`'s Users/Consumers section are checkers #59/#60/#61 — which don't exist yet — so the bug has no feedback path until those checkers are built weeks or months later. | An AI agent (or a human reviewing a future #59/#60/#61 PR) sees a nonsensical refactoring suggestion (e.g. "Pull Up Method" between two structurally unrelated classes, or a "Collapse Hierarchy" suggestion on an `implements` edge that should never trigger it) and has to trace it back through a feature that shipped and was "done" long ago. | Plan.md currently has no correctness check that doesn't depend on #59/#60/#61 existing. Add a self-contained invariant test to Story 1.6.1/1.6.2 that runs in this feature's own CI, independent of any downstream checker: every `resolved: true` edge's `to` id must actually exist in `model.packages` as a `Type`/`Interface` `SymbolNode`, and every edge's `kind`, when `Some`, must agree with the target's actual `SymbolKind` (`Type -> Extends`, `Interface -> Implements`) whenever `kind_hint` was `None` (i.e. the inferred-kind path never silently disagrees with the index it read from). This converts "wait for a downstream checker to notice" into "CI catches structural corruption at merge time." | P1 |
| 2 | Epic 3.2 (plan.md Story 3.2.1) commits real-world backtest validation only for Kotlin — a brand-new corpus repo plus a 20-sample manual spot-check — while Go/Java/TS/JS extraction, which is 4 of the 6 dispatch languages and the majority of the task count, ships validated against hand-written fixtures only, even though the existing 14-repo corpus (`kubernetes/kubernetes` for Go, `apache/cassandra` for Java) already contains both patterns `research/pitfalls.md` §2 flags as fixture-blind spots (Go interface-embeds-interface, Java `interface Foo extends Bar, Baz` with multiple targets). The asymmetry isn't because those three languages are provably lower-risk — Java's interface-to-interface case is a real "syntactically unambiguous but easy to mis-tag" trap the plan itself had to special-case (Story 1.4.2) precisely because a naive class-shaped extractor would get it wrong. | A future PR for #59 (Go-heavy, since kibitzer's own codebase is Go) surfaces a Pull-Up-Method suggestion that turns out to be based on a `type_edges` entry that was never checked against a single real Go file, only hand-written fixtures. | Add one task alongside 3.2.1b (already flagged as an open Concern in `adversarial-review.md`, unaddressed by the last repair pass) that runs `kibitzer architecture export` against 1-2 already-cloned corpus repos per language family (e.g. `kubernetes/kubernetes` for Go, `apache/cassandra` for Java, `denoland/deno` or `microsoft/vscode` for TS) and spot-checks a sample of `type_edges` the same way Story 3.2.1 does for Kotlin — reusing already-cloned repos, so the marginal cost is a `kibitzer` run plus a manual scan, not a new clone. | P2 |
| 3 | The plan's own task-level time estimates (labeled "~X min" on all 38 tasks) sum to roughly 148 minutes (~2.5 hours) of stated work, which is off by roughly one to two orders of magnitude from `requirements.md`'s stated appetite of "Small–Medium (3-8 days)" — and the gap is never reconciled anywhere in the plan. For a solo maintainer running this through `subagent-driven-development` (fresh subagent + dual review per task, 38 times), the actual wall-clock cost is dominated by per-task dispatch/review overhead the "~X min" labels don't account for at all, so neither number is a reliable estimate of what actually landing this plan costs. | Implementation runs several days longer than the per-task labels implied, and — because there's no explicit checkpoint in the plan for "is this still worth finishing" — either stalls mid-way (e.g. some of the 18 `ArchModel { ... }` struct-literal sites in Task 1.1.1c updated, others not, leaving the crate non-compiling on a stale branch) or gets rushed through its later, easier-to-skip tasks (the Kotlin corpus clone-and-spot-check, Task 3.2.1b, is explicitly manual/unverified-by-CI and the easiest task to silently skip under time pressure). | Before Phase 5 implementation starts, reconcile the two numbers explicitly: either revise the per-task labels to reflect realistic subagent-dispatch-plus-review cost, or add a line to plan.md's Appetite/Dependency Visualization section stating which of the 9 epics are truly required for a mergeable v1 versus which (Epic 3.1 perf fixture, Epic 3.2 Kotlin corpus) could ship as a fast-follow PR without blocking #59/#60/#61 from starting on the core `type_edges` capability. | P2 |
| 4 | `TypeRelationEdge.kind: Option<TypeRelationKind>` has no documented contract for what a downstream consumer (a human or an LLM agent writing #59/#60/#61 later, reading `type_edges` as a raw library field, not through a self-describing MCP tool) is supposed to do with `kind: None` — and `None` is not a rare corner case: it's the outcome for essentially every unresolved external-base Go embed (`sync.Mutex`, `io.Reader` from an unindexed package) and every genuinely ambiguous Kotlin bare-`type` entry, which are common, not exotic. Nothing in the plan stops a future implementer from writing `edge.kind.unwrap_or(TypeRelationKind::Extends)` or a catch-all `_ => Extends` match arm as a "safe default" — silently reintroducing exactly the guessing `resolve_in`'s doc comment (quoted approvingly throughout this plan) says the codebase never does. | A future #60/#61 PR's own code review misses a `.unwrap_or(Extends)` or equivalent default, and it isn't caught until a Kotlin or Go-heavy repo starts producing Collapse-Hierarchy suggestions on what were actually `implements` (or unknown) relationships. | Add a one-line contract to `TypeRelationEdge`'s doc comment in Task 1.1.1a (plan.md ~line 166-174): state explicitly that `kind: None` means "unknown — do not default to `Extends` or `Implements`; a consumer that cares about the distinction must treat `None` edges as unclassified, not skip silently or guess," so the constraint is visible at the type definition, not only inferable from the Pattern Decisions table's prose. | P2 |
| 5 | Requirements explicitly and correctly scope out Go structural interface satisfaction (a type satisfying an interface purely by having the right method set, with no `extends`/embedding keyword anywhere in source) — but this is the *dominant* way idiomatic Go code expresses "implements" (most of `kubernetes/kubernetes`'s interface satisfaction is structural, not embedding-based). The `list_supertypes`/`list_subtypes` tool descriptions drafted in Task 2.1.2d (plan.md ~line 586) never mention this gap — they describe `resolved: false` (unresolved external base) and `node_kind`/`hint` (wrong node kind) but say nothing about "a Go type can structurally implement an interface this tool will never report." | An AI agent calls `list_subtypes` on a well-known Go interface (e.g. one used throughout the target repo), gets back an empty or near-empty `edges` list because none of its real implementers use embedding, and — with nothing in the tool's own self-description warning otherwise — reasonably concludes "nothing implements this," then acts on that as ground truth (e.g. skipping a refactor that should have applied structural implementers too). | Add one sentence to both tool descriptions in Task 2.1.2d stating the Go-specific limitation explicitly: "For Go, this only reports interface satisfaction expressed via struct embedding — Go's structural (method-set-only) interface satisfaction is not detected; an empty result for a Go interface does not mean nothing implements it." This is a text-only change to an already-planned task, not new scope. | P2 |
