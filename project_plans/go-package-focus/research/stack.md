The `GoKind` enum (the typed wrapper around tree-sitter node kind strings) is

## Tree-sitter Go node kinds used today

`src/import_graph.rs` walks the following node kinds for Go:

| Kind | Role |
|------|------|
| `source_file` | Root node (import walk starts here) |
| `package_clause` | Locating a file's `package` declaration |
| `package_identifier` | The identifier child of `package_clause` |
| `import_spec` | Individual import path within an import block |

The `import_spec` node has two named child fields: `name` (optional alias) and
`path` (the string literal). The function `collect_go_imports` extracts the
path text and its line number; `go_import_spec` additionally extracts the alias.

Additional named kinds available from the go.json grammar that are relevant to
a package-split evidence report:

- `function_declaration`, `method_declaration` — counting exported functions per package
- `type_declaration` / `type_spec` — counting type definitions
- `struct_type`, `interface_type` — distinguishing data types from interfaces
- `selector_expression` — cross-package field/method references (for coupling evidence)
- `const_declaration`, `var_declaration` — other top-level declarations

## fan_in_out bug: root-cause confirmation

`fan_in_out` in `src/architecture_checks.rs` (line 180–187) iterates
`edges: &[ImportEdge]` and increments counters once per edge. `ImportEdge`
has `{ from, to, file, line }`: a single logical `(from, to)` package
relationship produces one `ImportEdge` per import *statement* (a file with two
imports from the same target produces two edges). The result is that
`fan_out`/`fan_in` counts raw edges rather than distinct `(from, to)` pairs.

<!-- kibitzer:ignore missing-paragraph-break -- fix options for the same problem, not a topic shift -->
Fix: deduplicate on `(edge.from.as_str(), edge.to.as_str())` before counting.
A `HashSet<(&str, &str)>` built first, then iterated, achieves this with no
allocation outside the function's stack frame. Alternatively, sort and
`dedup_by_key` on a `Vec<(&str, &str)>` collected from the edges.

## Existing Go invocation patterns

There are **no existing `go build`, `-toolexec`, or `-debug-actiongraph`
invocations** in the codebase. Every `std::process::Command` call in `src/`
invokes `git`, `sh`, `ps`, `sleep`, `kill`, or `tar`. Go source is analysed
purely statically via tree-sitter; the go CLI is never spawned.

This means the build-cost collector prototype introduces the repo's first
`Command::new("go")` call. The existing `git_cmd.rs` / `check.rs` patterns
for running an external command and capturing stdout/stderr are the right
model to follow.

## Build-cost collector: Go toolchain targeting

The only Go version pin in the repo is in the dogfood fixture:

```
testdata/dogfood-architecture/go.mod → go 1.21
```

Relevant Go release notes for the prototype:

- `-debug-actiongraph` (writes a JSON action graph to a file): available since
  Go 1.12. The flag is passed to `go build` or `go test`, not to a separate
  subcommand. Invoke as:
  `go build -debug-actiongraph=<path.json> ./...`
- `-toolexec` (interposes each compiler/linker invocation): available since at
  least Go 1.5, stable interface. Invoke as:
  `go build -toolexec='<wrapper> %s %a' ./...`
- Both flags require that the working directory contain a valid `go.mod`.

For the prototype, `-debug-actiongraph` is lower-friction: it writes structured
JSON without requiring a wrapper binary. Prefer it for the first pass; add
`-toolexec` later if per-action timing is needed.

No minimum Go version higher than 1.21 is required by either flag, but
practically any Go version a user is likely to have (≥ 1.20) supports both.

## Testdata fixture structure

```
testdata/
  dogfood-architecture/
    go.mod              → module dogfood.example/app, go 1.21
    domain/domain.go    → package domain; deliberate import of infra (coupling violation)
    handlers/handlers.go
    infra/infra.go
  comment-quality-corpus/   → unrelated (NLP corpus)
```

The dogfood-architecture fixture is already used by `architecture_checks.rs`
integration tests and the `InstabilityChecker` / `CouplingChecker` tests. It is
the right place to add `go-package-focus` test cases: add a new package
directory (e.g. `testdata/dogfood-architecture/wide/`) whose files import many
other packages to trigger the advisory check.

The fixture module uses the import path `dogfood.example/app/<subdir>`.
`go_package_identity` derives the package key from `go.mod` + relative path, so
a new subdirectory is automatically picked up with no fixture code changes
beyond adding the `.go` file.

## Summary for implementation

1. **Bug fix** — change `fan_in_out` to collect `HashSet<(&str, &str)>` of
   distinct `(from, to)` pairs before counting fan-out/fan-in per node.
2. **go-package-focus check** — new `ArchitectureChecker` operating on
   `ImportGraph`; iterates nodes, computes inbound/outbound distinct-pair counts
   (reusing the fixed `fan_in_out`), and emits evidence-report findings for
   packages that are candidates for splitting (high fan-out) or extraction into
   a shared library (high fan-in).
3. **Build-cost collector** — `Command::new("go").arg("build")
   .arg(format!("-debug-actiongraph={path}")).arg("./...")`, run in the repo
   root; parse the resulting JSON; emit per-package compile-time evidence
   alongside the coupling findings. No new Rust dependencies needed — `serde_json`
   is already in `[dependencies]`.
