# Pre-mortem: checker-plugin-system
**Date**: 2026-09-06

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | Install is silently machine-wide (Step 0.5's chosen design): a plugin installed once keeps firing in *every* repo forever, and the only disclosure is a one-time stdout line at install time that's easy to forget weeks later. | A `kibitzer run`/hook/MCP invocation in an unrelated repo suddenly surfaces a plugin's finding or runs noticeably slower, and the user doesn't connect it to a `plugin install` from a different project weeks earlier. | Make the disclosure durable, not one-shot: have `kibitzer run`/hook output note "(N machine-wide plugin check(s) active)" whenever `registered_plugin_checks()` is non-empty, so every run — not just the install command's terminal scrollback — carries the reminder. | P2 |
| 2 | The persistent daemon (`kibitzer daemon start`, the primary path for Claude Code hook/MCP calls) doesn't observe `plugin install`/`remove` because `config_stamp` never fingerprints `registry.json` — it keeps serving a stale check list, including invoking a just-removed plugin's now-deleted binary. | CLI `kibitzer run` shows the correct, up-to-date check list, but agent-driven hook/MCP calls (routed through the daemon) either miss a just-installed plugin's findings or throw an exec/not-found error for a just-removed one — a "works in the terminal, broken in the agent" split with no `.claude/inspect.json` diff to explain it. | Implement the fix adversarial-review.md already scoped as "small, contained" (fold the registry file's mtime/hash into `config_stamp` in `cache.rs`/`daemon.rs`) instead of documentation-only; at minimum, have `plugin install`/`remove` detect a running daemon and refuse to complete silently — print a hard warning or auto-restart it. **RESOLVED** (plan-repair, 2026-09-06): plan.md's Tech Debt Disposition row for `src/cache.rs` now specifies the concrete fix (a `registry_stamp: Option<Stamp>` field on `CacheEntry`), implemented as Story 4.1.2 with its own Given-When-Then and unit tests. | P1 |
| 3 | SARIF turns out too lossy for the mechanism's actual first real consumer (the embedding "how vs why" checker) — no field carries a confidence score or the specific comment/identifier pair — so the mechanism ships but has to be partially redesigned before it solves the problem it exists for. | When the embedding checker is later built as a plugin, its findings have no schema-legal place to put a confidence score, forcing either a lossy hack (encoding structured data into `message.text`) or a follow-up change to the check-dispatch/SARIF-parsing path. | Before Phase 5 sign-off, prototype the embedding checker's actual expected SARIF payload (a fake finding carrying a confidence value) against `src/check.rs`'s SARIF parser and record the answer — this is requirements.md's own named Feasibility Risk, currently unactioned in plan.md. | P2 |
| 4 | The hand-rolled `parse_plain_version` (ADR-003) only accepts exactly `MAJOR.MINOR.PATCH` — any prerelease/build-metadata suffix (`0.2.0-rc1`) or shortened form (`"0.2"`) makes it bail with a raw parse error, unrelated to actual version compatibility. | `kibitzer plugin install`/`status` starts failing with a `parse_plain_version` error the day the maintainer tags a kibitzer prerelease or a manifest author writes a non-3-part `min_kibitzer_version` — a previously-working install now errors opaquely. | Add a test case in Story 2.1.3 for a prerelease-suffixed/short version string, and decide explicitly (not by omission) whether to strip suffixes with a clear message or hard-reject with wording that names the real cause, rather than leaving the plan silent on the case. | P2 |
| 5 | The command-timeout fix's own documented escape hatch (Task 4.2.1a: hang risk above the ~64KB OS pipe buffer) is violated by exactly the plugin class this project exists to enable — a heavy embedding checker with large output — silently reintroducing the hang Epic 4.2 was built to eliminate. | A plugin that emits >64KB of stdout before exiting still stalls past `COMMAND_TIMEOUT`: the kill fires, but the child is blocked on `write()` rather than exiting, so `kibitzer run` hangs for the full duration the fix was supposed to bound. | Drain the child's stdout/stderr on a concurrent thread while waiting (matching `wait_with_output`'s own approach) with the timeout applied to the whole drain-and-wait, not just the wait; add an integration test with a command producing >64KB of output before exit to prove the accepted limitation doesn't defeat the fix for the mechanism's real intended use case. | P3 |

## P1 Items (address before implementation)
