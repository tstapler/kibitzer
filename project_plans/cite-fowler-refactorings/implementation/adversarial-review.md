## Concerns
- [ ] **Epic 1.3 (`docs/syntax-rules.md` update) has zero grounding in requirements.md** — it isn't named in any Acceptance Criterion, in "Out of scope," or anywhere else in the source document; it's an addition the plan author introduced. AC #6 explicitly makes `CATALOG` (Epic 1.2) optional, so that epic has textual cover; Epic 1.3 has none. For a Complexity-1 item whose own Problem/Proposal frames the change as "Pure message-copy change in two `format!` calls... in `src/rules.rs`" (singular file), touching a second file on spec-less authority is scope creep, even though it's marked optional. Recommendation: either cut Epic 1.3 entirely, or explicitly flag it to the item owner as an addition beyond the backlog item before doing it — don't let "optional" alone launder an unrequested file touch into the plan.
- [ ] **Two incompatible Fowler-citation phrasings will coexist in `src/rules.rs` after this change**, and the plan's own precedent claim slightly overstates the match. Pattern Decisions (plan.md line 29) cites `flag-argument` (`src/rules.rs:865`) as precedent for "inline string literal in the `format!` call" — true for the *mechanism*, but the *phrasing template* diverges: `flag-argument` uses `"...Fowler's Remove Flag Argument: split into two named functions..."` (mid-sentence, no URL), while the new messages use `"...consider Extract Function (https://...)"` (trailing parenthetical, with URL). Confirmed via `grep -rn 'https\?://' src/*.rs` that no existing `Finding.message` anywhere in the codebase embeds a URL — this is genuinely a new convention, not an extension of an old one (the plan's own research/pitfalls.md §5 says this explicitly; the plan.md Pattern Decisions table doesn't carry that caveat through). Low risk given requirements' explicit "no general catalog mechanism" scoping, but worth a one-line acknowledgment in the plan rather than implying continuity with an existing pattern that doesn't fully hold.
- [ ] **No follow-up if a refactoring.com URL 404s after ship.** Task 1.1.4a re-verifies immediately before merge, but there's no monitoring, no markdown-link-integrity-style periodic check, and no fallback (e.g., no non-URL description remains if the link rots) — a future site restructure silently degrades the message to a dead link with no signal to anyone. This is likely acceptable: the message is purely advisory text, AC #3 only requires "verified before ship" (not ongoing), and the codebase has no existing pattern for validating external message content post-ship either. Flagging as a concern rather than a blocker — worth an explicit one-line acceptance ("no ongoing liveness check; dead link degrades gracefully to a still-readable name") rather than silence.

This substantially de-risks the plan; most of the above concerns are refinements, not gaps in diligence.
