**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The two `refactoring.com` URLs 404/redirect/restructure after ship, and the accepted "no link-liveness check" gap (Pattern Decisions table, plan.md) has no owner or trigger to ever notice it happened | A user or maintainer stumbles on a dead link years later while reading a finding; nothing in CI or a scheduled job surfaces it proactively | Since re-adding automated checking is explicitly rejected as disproportionate, at minimum note the accepted risk in `validation.md` with a concrete re-check trigger (e.g. "re-verify both URLs next time this file is touched for any reason") rather than leaving it a silent, undiscoverable gap | P3 |
| 2 | Optional Task 1.1.3a (`CATALOG.description` edit) ships in an ambiguous state — done, skipped-and-forgotten, or skipped-on-purpose are all indistinguishable from the merged diff alone, compounding the ambiguity adversarial-review.md's Concern #1 already flagged in the plan's own internal inconsistency | A PR reviewer or future contributor can't tell from the PR whether 1.1.3a was a deliberate scope cut or an oversight, and either re-does unnecessary work or ships a 2-of-4-vs-2-of-5 inconsistent `CATALOG` indefinitely | Plan.md or the PR description must state explicitly which outcome was chosen ("1.1.3a included" or "1.1.3a skipped, tracked as follow-up #N") — not leave it implicit in whether the diff happens to include it | P2 |
| 3 | `CATALOG.description`'s "40 lines" / "4 levels deep" are literal hardcoded text (unlike the runtime `format!` messages, which interpolate `LONG_FUNCTION_LINES`/`MAX_NESTING_DEPTH` live) — a future contributor bumping either constant has no compiler or test signal that the description text now lies, and this PR extends that same hardcoded-number pattern rather than flagging it | A user reads a `long-function` `CATALOG` description saying "more than 40 lines" while findings actually trigger at a different threshold (post-bump), with no test failure anywhere pointing at the mismatch | Add a `mod tests` assertion that `CATALOG[0].description` and `CATALOG[1].description` contain `LONG_FUNCTION_LINES.to_string()`/`MAX_NESTING_DEPTH.to_string()` (or format the description via `const`-friendly interpolation), so a future threshold change fails a test instead of silently going stale — not addressed by plan.md's Tech Debt Disposition ("None identified") | P3 |
| 4 | The two new tests (`long_function_message_cites_extract_function`, `deep_nesting_message_cites_guard_clauses`) hand-rebuild the same 45-line/5-level-nested Go fixtures already used by `flags_long_function`/`flags_deep_nesting`, rather than sharing a helper — a future threshold or fixture-shape change now has 4 places to update instead of 2, and missing one produces a confusing failure or a stale-but-still-passing fixture | `cargo test` fails in exactly one of the four fixture-bearing tests after an unrelated future change to `LONG_FUNCTION_LINES`/`MAX_NESTING_DEPTH`, with no obvious link between the failure and the edit that caused it | Task 1.1.2a should factor fixture construction into a shared private test helper (e.g. `fn long_function_src(lines: usize) -> String`) reused by both old and new tests, or at minimum comment at each duplicated fixture that it must be kept in sync with its sibling | P3 |
| 5 | Task 1.2.1a's URL check uses `curl -sI` (HEAD) run once before opening the PR; a HEAD 200 doesn't guarantee a real browser's GET behaves the same (some sites special-case HEAD), and nothing re-checks between "verified before PR" and actual merge/release | A finding ships linking a URL that returns 200 to `curl -sI` but 403/404/redirect-loop to an actual GET click-through, discovered only when a user reports the link doesn't work | Verify with a GET-based check instead (`curl -so /dev/null -w '%{http_code}' <url>`), and note in validation.md that Task 1.2.1a's result is a point-in-time check, not a standing guarantee, so nobody later treats "verified" as evergreen | P3 |
