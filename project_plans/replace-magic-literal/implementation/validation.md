# Validation Plan: replace-magic-literal

**Date**: 2026-09-22

## Happy Path Scenario
Given a Go file whose `SyntaxRulesChecker` is run via kibitzer's default catalog, when the file contains the same non-trivial numeric literal (e.g. `86400`) written twice with no bound named constant, then `check()` returns exactly one `[replace-magic-literal]` `Finding` anchored at the first occurrence and listing the second occurrence's line inline.

## Requirement → Test Mapping

Test names follow this file's existing `src/rules.rs` convention: `<lang_prefix>_flags_<rule>` for a true positive, `<lang_prefix>_allows_<rule>_<condition>` for a confirmed non-fire, `go` has no prefix (bare `flags_`/`allows_`). All tests below live in `src/rules.rs`'s `#[cfg(test)] mod tests` unless noted otherwise. Per Story 2.1.1's own acceptance criterion ("representative — not duplicated 8x"), Go carries full detail (happy/error/allow-list/exclusion/generated-guard); TS/Python/Java/Kotlin/Rust each carry one true-positive + one exclusion test, matching Epic 2.1's task breakdown.

Because this rule's only externally observable behavior is through `SyntaxRulesChecker::check()` (unlike `long-function`/`deep-nesting`, which are directly reachable via `walk_declarations` alone), most "unit" tests here already exercise the full collect→resolve→emit pipeline (`walk_literals` → `resolve_excluded_constants` → `emit_literal_findings`) inside `check()`. The Unit/Integration split below is by scope (single-language mechanical fixture vs. realistic/cross-cutting fixture), not by whether `check()` is called.

## Test Stack
- **Unit**: Rust's built-in `#[test]` harness (`cargo test --lib`), `assert!`/`assert_eq!`/`assert_ne!` — no external assertion crate, matching every existing test in `src/rules.rs` and `src/config.rs`.
- **Integration**: Same harness, in-process (`SyntaxRulesChecker::check()` / `config::default_checks()` called directly against `tree_sitter` parses of inline fixture strings) for the per-rule integration tests; one true out-of-process integration test (`tests/`-directory style, matching `tests/false_positives_cli.rs`'s pattern of invoking `env!("CARGO_BIN_EXE_kibitzer")`) is *not* required for this feature — the config-layer test (`default_config_flags_repeated_literal_with_no_inspect_json`) exercises the same dispatch path in-process, which is proportionate to this feature's "Small" appetite. The corpus/transcript backtests (AC7-8) are external, script-driven validation activities (`docs/backtesting.md`, `docs/backtest-repos.md`), not part of the `cargo test` suite.
