# Pre-mortem: replace-magic-literal
**Date**: 2026-09-22

## Failure Modes

| # | Failure | First Symptom | Prevention | Severity |
|---|---------|--------------|------------|----------|
| 1 | The `>=2` threshold reproduces `duplicate-code`'s own documented failure: table-driven test fixtures and repeated status/config literals dominate findings, flooding a *default-on* check across every kibitzer install. | Maintainers/users report `replace-magic-literal` firing dozens of times per `_test.go`/parametrized-test file; the Claude Code `PostToolUse` hook starts nagging on every edit that touches a table of expected values. | Make Story 3.2.2's bump rule quantitative and binding (e.g. "if ≥40% of triaged corpus findings are test/fixture literals, `MAGIC_LITERAL_MIN_OCCURRENCES` bumps to 3 before merge — no exceptions"), not a judgment call to be made *after* seeing the numbers. Also default-scope test files out of this rule the way `duplicate-code`'s own postmortem eventually recommended doing but never executed on. | P1 |
| 2 | AC7/AC8's backtest steps produce evidence but nothing forces the plan to act on unfavorable evidence — `docs/duplicate-code-false-positives.md` shows this exact shop already did this once: a documented ~60% false-positive rate from table-driven-test literals was logged as "needs discussion" and never fixed. The same rationalization ("real duplication/magic literals by the checker's own definition") is available here. | The PR merges with a backtest-triage `.jsonl` file committed, `MAGIC_LITERAL_MIN_OCCURRENCES` still at 2, and a PR-description sentence saying the FP rate is "acceptable" with no numeric bar it was checked against. | Add a merge-blocking assertion to validation.md: the PR description must state the actual computed true/false-positive ratio next to a pre-committed numeric bar (not chosen after seeing the data), and CI (or a pre-merge checklist item) must fail/flag if `docs/backtest-triage/*/replace-magic-literal.jsonl` is absent or has zero verdict entries. | P1 |
| 3 | Per-language allow-list gaps (already flagged in adversarial-review.md): `MAGIC_LITERAL_ALLOWLIST`'s fixed raw-text list (`"0"`, `"1"`, `"-1"`, `"\"\""`, `"''"`) never matches Kotlin's empty triple-quoted string, Rust's `r""`/`r#""#`, or Go's backtick empty raw string — a direct AC3 violation for exactly the 3 languages whose `literal_kinds` include those forms. | A Kotlin or Rust repo gets `[replace-magic-literal]` findings on an empty multiline/raw string repeated twice, contradicting the documented allow-list guarantee; nobody notices until backtest touches a repo using that literal form, or a user files a confused bug. | Normalize each literal's raw text (strip per-language delimiters/prefix) before allow-list comparison, or make the emptiness check structural rather than a fixed string list (adversarial-review.md's own recommendation). Add one allow-list regression test per affected language (Kotlin, Rust, Go raw string), not just Go's Task 2.1.1b, so the fix is locked in rather than re-broken by a future edit. | P2 |
| 4 | The same-file, non-scope-resolved "referenced elsewhere by name" exclusion is a raw-text identifier match with no scope resolution — a coincidentally-named, unrelated binding elsewhere in the file (e.g. two independent `const Timeout` in different functions, or a struct field sharing a constant's name) silently suppresses a genuine, unrelated magic-literal violation. This is a false negative, so it fails silently: the checker looks like it's working (no crash, no noisy false positive) while quietly missing the smell it exists to catch. | A reviewer manually spots an obvious repeated literal (e.g. `3600` three times in unrelated functions) that kibitzer never flagged, and debugging why takes real time since the suppression has no visible trace (no "excluded because bound to X" log). | Land the adversarial-review's requested fix: state the const-reference-scope decision explicitly in ADR-001 (same-file including own function vs. cross-function-only), and add both a same-function-only reference test and a coincidental-name-collision test so the behavior is deliberate and regression-locked rather than incidental. | P2 |
| 5 | Epic 1.0's mechanical `lang_config()` extraction (8 match arms → 8 hand-written constructor functions) is verified only by "existing tests still pass unchanged" — but the existing tests are behavioral (assert on `Finding`s for specific fixtures), not field-level assertions on every `LangRuleConfig` value, so a transcription slip (a struct-literal field copied into the wrong constructor, or a `..typescript_lang_config()` base misapplied to `tsx`/`javascript`) can silently ship as a regression in one of the 4 *pre-existing* rules for one language — attributed later, if ever, to the wrong PR. | Weeks after merge, `long-function` or `deep-nesting` stops firing (or starts misfiring) for one specific language in one specific repo, with no obvious link back to the "add replace-magic-literal" PR that actually caused it. | Add a temporary equivalence check to Task 1.0.1b: capture `lang_config()`'s output (e.g. `format!("{:?}", cfg)` per language, or an explicit field-by-field assertion) before the extraction and diff it against the post-extraction output for all 8 languages, not just "full suite passes" — then delete the temporary probe once confirmed, matching the pattern Task 1.1.1b already uses for the `-1` probe. | P2 |

## P1 Items (address before implementation)
- [ ] Failure #1 — Rewrite Story 3.2.2's threshold-decision AC to state a pre-committed numeric false-positive bar (e.g. ≥40% test/fixture-literal share triggers an automatic bump to 3) instead of a post-hoc judgment call, and add a default test-file scoping exclusion to close off the exact table-driven-test failure mode `duplicate-code` already hit.
- [ ] Failure #2 — Add a merge-blocking requirement to validation.md/Phase 3 that the PR description states the actual computed true/false-positive ratio against that pre-committed bar, and that a missing or empty `docs/backtest-triage/*/replace-magic-literal.jsonl` blocks merge — closing the gap where `duplicate-code`'s own 60% false-positive finding was logged and never acted on.
