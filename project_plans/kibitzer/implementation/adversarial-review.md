## Concerns

- [ ] **"Each phase is independently mergeable/revertable" (line 10) overstates what the plan's own Dependency Visualization diagram shows.** The diagram has Phase 4/5 converging on *both* Phase 1 and Phase 2/3, Phase 6 explicitly "touches every checker from Phases 1-5," and Phase 7's verification (Task 7.1.1d) hard-depends on Story 1.2.2's CLI verb from Phase 1. Only a strict reverse-order revert is actually safe — reverting e.g. Phase 2 alone after Phase 3-7 have merged breaks Phase 3 (`NamingChecker` reuses `DeclarationGraph`), Phase 4.3/5.3 (extend `declarations.rs`), and Phase 7 (dogfoods `content-rules`). Story 2.2.3's addition strengthens this further: it puts a piece of Phase 2 logic (`check_native_against_git_head_repo`'s Declaration-kind branch) inside `check.rs`, a file Phase 1's Story 1.2.1 also modifies — one more thread tying Phase 1 and Phase 2 together at the same call site. — **Recommendation**: reword the claim to "revertable in reverse phase order" and drop "independently."
- [ ] **The Phase 1→Phase 2 forward-reference stub (Task 1.2.1a) is itself evidence the two phases aren't cleanly separable at the code level.** The task instructs stubbing `declaration_checks::lookup` to return `None` unconditionally if Phase 1 lands before Phase 2 exists, then replacing it in Task 2.1.3b. That's a real coupling between two phases the plan otherwise markets as independent — a partial revert of either phase after the other has landed leaves a dangling stub/replacement mismatch. — **Recommendation**: either sequence Phase 0+1's dispatch scaffolding to land the (empty) `declaration_checks` module up front, or explicitly document Phase 1/2 as a single revert unit.
- [ ] **`declarations::build()`'s error path through the new Declaration dispatch branch (Task 1.2.1c) is still unspecified — not addressed by Story 2.2.3.** The existing Import branch has an explicit `Err` → failed-`CheckResult` pattern (`src/check.rs:813-825`); Task 1.2.1c's description ("build `DeclarationGraph` via `crate::declarations::build(...)`, call `.check()`") is unchanged from the prior pass and still never states equivalent handling, and no AC in Story 1.2.1 or 2.2.2 tests a `declarations::build()` failure. Note this is a *different* call site than the one Story 2.2.3 fixed: Task 2.2.3b does specify error handling for the git-HEAD-snapshot recheck path (`.ok().map(...)`, mirroring the Import branch, verified against Task 2.2.3b's text) — but that specification doesn't cover Task 1.2.1c's main dispatch path, which is the one this concern is actually about. — **Recommendation**: add the mirrored AC/test explicitly to Story 1.2.1 or 2.2.2 rather than leaving it to implementer judgment.
- [ ] **No acceptance criteria anywhere test the new AST walkers against malformed/incomplete source** — despite this being one of the two most obviously relevant failure modes for this feature. `parser.parse()` in tree-sitter essentially never returns `None` for a syntax error (it produces an error-recovery tree with `ERROR`/`MISSING` nodes instead, so the existing `Result`-propagation path in `import_graph.rs`/`declarations.rs` won't even trigger). The real risk is downstream: Java/Kotlin's import/declaration walk is explicitly **positional** ("`kind()`-filtered positional child walk, no field names" — Pattern Decisions), which is exactly the shape most likely to panic or silently misclassify when error recovery produces fewer/different children than the hand-verified fixture in Story 4.1.1/4.1.2. — **Recommendation**: add one malformed/incomplete-source fixture test per new extractor (Go/JS declarations in Phase 2, Java/Kotlin in Phase 4, Python in Phase 5) asserting no panic and a reasonable (possibly empty) result.
- [ ] **Phase 4's 4-5h sizing has no contingency for its own self-identified worst case.** Epic 4.2's stated goal is "one generic resolver... 3 small tables, 1 shared implementation" reusing `QualifiedImportLangConfig` across Go/Java/Kotlin. But Story 4.1.2 is honest that Kotlin has "no reference queries anywhere" and flags the aliased-import shape as "not confirmed from static schema data." If the real `to_sexp()` output (Story 4.1.2) turns out not to fit the shared qualified-name family, Kotlin needs a bespoke resolver like Python's own (Phase 5, sized 3-4h on its own) — and nothing in Phase 4's sizing, sequencing, or tasks budgets for that branch, despite it being called "the highest-risk sub-task in this plan" and "flagged consistently by 2 of 6 research agents." — **Recommendation**: treat Story 4.1.2 as an explicit go/no-go gate with a stated fallback estimate (e.g. "+3h, reuse Python's bespoke-resolver shape") rather than an implicit hope that it fits.
- [ ] **Dogfooding (Phase 7) only exercises the mature Go extractor.** The fixture, CLI verification (Task 7.1.1d), and `.claude/inspect.json` wiring (Story 7.1.2) are all Go-only, unchanged by this iteration. Java, Kotlin, and Python — the plan's newest, least-verified, and (per Phase 4's own sizing note) riskiest code — get no end-to-end integration proof through the real dispatch/CLI/MCP path, only hand-written unit tests against hand-picked fixtures. The riskiest new code is the least dogfooded. — **Recommendation**: at minimum, add one Java or Kotlin file to the dogfood fixture exercising `component-deps` before calling Phase 7 "proof the feature works end-to-end."

## Minors

- Task 6.2.2c claims updating "the one call site" of `render_dependency_graph` (in `mcp.rs`), but `src/mermaid.rs`'s own test module has 5 more call sites that also need the new `components: &[Component]` parameter (`src/mermaid.rs:109,125,138,147,158`) — 6 total, not 1. Trivial to fix, but worth correcting given the plan's own "no completion claim without proof" standard.
- Unresolved Question #1 slightly overstates the tension it resolves: requirements.md's Success Metric is satisfied by "`kibitzer check native <checker> <path>` **/** the `architecture_assessment` MCP tool" (either, per the "/"), and the MCP tool path is already covered by Story 2.2.2. Story 1.2.2's new CLI subcommand is a reasonable value-add for dogfooding's "run it, don't read it" testability, but it isn't strictly required by the letter of the metric the way the Unresolved Question frames it.
- `ContentRule.allowed_kinds` / `NamingRule.kind` string values are never validated against the fixed `DeclKind` vocabulary at config-load time, unlike `Component` name references (Story 0.1.3's Levenshtein-checked validation). The failure modes are asymmetric but not unguarded: a typo'd `allowed_kinds` entry produces a false-positive flood (self-revealing on first run), and a typo'd `NamingRule.kind` is caught by the existing zero-match advisory (Story 3.1.2). Still, for consistency with how `DependencyRule` references are treated, a config-load-time check would close the gap cheaply.
- Once both an Import-based and a Declaration-based checker are configured for the same repo (e.g. `component-deps` + `content-rules`), every source file gets parsed twice per batch run — `import_graph::build()` and `declarations::build()` each construct their own uncached `tree_sitter::Parser` per file, per ADR-001's explicit choice not to share `GrammarCache` between the two passes. No stated performance SLO is violated (batch-only trigger, requirements.md sets no tight budget), but it's a real, quantifiable, undocumented cost given `GrammarCache` exists specifically to avoid exactly this pattern.
- **(New this iteration)** `run_architecture_check`'s `passed = findings.is_empty()` (`src/check.rs:828`) doesn't account for `ArchFinding.severity_override` — a `Blocking`-severity check whose *only* finding is a zero-match advisory (`severity_override: Some(Advisory)`, from Story 1.1.3's `zero_match_advisory<T>`) still computes `passed == false` and triggers `check_native_against_git_head_repo`. Checked whether Story 2.2.3 introduces or worsens this: it does not — `passed`'s computation is untouched by Story 2.2.3, and the same behavior already applies identically to Phase 1's `component-deps` (Import-kind, already dispatched through the baseline-downgrade path since Phase 1, before Story 2.2.3 exists). Orthogonal to the git-HEAD-baseline dispatch fix and not a blocker for it, but worth a follow-up story if zero-match-only "blocking" checks turn out to matter in practice.

## Resolved this iteration

- [x] **Blocking-severity `content-rules`/`naming-rules` checks silently never got the "predates your edits" HEAD-baseline downgrade every other native architecture checker gets — now resolved by Story 2.2.3.** Re-verified directly against `src/check.rs:840-935` (current source, unmodified by this planning pass — implementation is Phase 5): `check_native_against_git_head_repo`'s lookup at line 872 is still `crate::architecture_checks::lookup(arch_name)?`, i.e. the real bug still exists in the codebase today, exactly as the plan itself states (line 859: "Verified directly against `src/check.rs:867-931` before writing this story"). Story 2.2.3 (`project_plans/kibitzer/implementation/plan.md:845-933`) specifies a concrete, technically sound fix:
  - **(a) Import vs. Declaration branching**: Task 2.2.3a swaps the lookup for `lookup_any_architecture_checker(arch_name)?` (returning the `AnyArchitectureChecker` enum from Story 1.2.1/Task 1.2.1a), and Task 2.2.3b branches on it — `Import(checker)` keeps the existing `import_graph::build` + `.check()` path unchanged, `Declaration(checker)` adds `declarations::build(&snapshot_dir, &files, &arch_config.effective_components())` + `.check()`, reusing the *same* `files` list already collected by the existing `walk_and_collect_files(&snapshot_dir)` call (`src/check.rs:921`) — no restructuring of the snapshot/archive machinery needed. The `declarations::build` signature it calls (`fn build(repo_root: &Path, files: &[PathBuf], components: &[Component]) -> Result<DeclarationGraph>`, plan.md:684) and `effective_components()` accessor (defined in Phase 0, Task 0.1.2c, plan.md:289-290) both already exist as named elsewhere in the plan — no dangling references.
  - **(b) Given-When-Then concreteness**: the AC (plan.md:872-890) names real data, not placeholders — a specific `ContentRule` (component `domain`, `allowed_kinds: ["struct"]`), a specific violating declaration (a `Validate` function), and three concrete scenarios (predates HEAD → downgrades to `Some(false)`/`Advisory`; new since HEAD → stays `Some(true)`/`Blocking`; same proven for `naming-rules` to show genericity). Backed by two new named tests (Task 2.2.3c/d: `content_rules_blocking_violation_downgrades_when_it_predates_head`, `naming_rules_blocking_violation_downgrades_when_it_predates_head`) plus an explicit regression test for the Import-kind path (`import_kind_checker_head_baseline_downgrade_still_works_through_dual_registry_dispatch`) — independently confirmed via `grep` that `check_native_against_git_head_repo` has genuinely zero existing test coverage today (no test in `src/check.rs`'s test module references it or names `layering`/`import-cycles`/`coupling`; the existing `TempRepo`-based tests at `src/check.rs:1391,1449` all exercise the separate shell-based `check_against_git_head`/`check_against_git_head_repo` functions, not the native one), so the plan's claim that this is new coverage, not a rerun, is accurate.

Story 2.2.3 is correctly sequenced inside Phase 2 (after Story 2.1.3 makes `declaration_checks::registry()` real), not Phase 1, matching the plan's own stated reason ("neither [Declaration-kind checker] exists before Phase 2's `declaration_checks::registry()` lands").
  - **(d) `severity_override` interaction**: checked, confirmed orthogonal — see the new Minor above. `check_native_against_git_head_repo`'s pass/fail computation (`checker.check(&graph, arch_config).is_empty()`) and `run_architecture_check`'s `passed` field don't reference `severity_override` at all, so Story 1.1.3's per-finding rendering plumbing doesn't interact with Story 2.2.3's dispatch fix in either direction.
  - Cross-checked the surrounding plan changes for consistency: the Domain Glossary's `AnyArchitectureChecker` row (plan.md:56), Pattern Decisions' new git-HEAD-baseline-downgrade row (plan.md:80), the Dependency Visualization diagram's Phase 1/Phase 2 boxes (plan.md:159-168, explicitly noting Phase 1's checkers were "already HEAD-baseline-downgradeable" and Phase 2 "closing the BLOCKER"), and ADR-001's Consequences-section addition (`project_plans/kibitzer/decisions/ADR-001-declaration-checker-third-trait.md:78-89`, adding `check_native_against_git_head_repo` as a third indirection-layer call site "caught by adversarial review during Phase 3 planning") all tell the same consistent story with no dangling references or contradictions against earlier phases.
