# Requirements: Mechanical Refactoring Engine

**Item:** Mechanical refactoring engine — plan/simulate/apply behavior-preserving refactors, exposed via MCP and the architecture checker
**Project name:** `mechanical-refactor-engine`

## Background

Kibitzer detects structural problems (package focus, hotspots, call-graph coupling) but cannot act on them. An agent told "package X is too broad" must improvise the move by hand: rewrite imports across every importer, fix test packages, re-run the build, and discover import cycles only after the edit. This umbrella adds a deterministic, behavior-preserving refactoring engine that:

1. Answers feasibility questions over the existing `ArchModel` (read-only, no writes)
2. Produces `RefactorPlan` objects listing ordered edits, touched files, and verification steps
3. Applies plans atomically or rolls back on failure
4. Verifies the result with the language's own toolchain
5. Exposes all three phases (simulate / plan / apply+verify) as MCP tools

## Staged scope (three sub-issues)

### Stage 1 — Feasibility and what-if simulation (#154, ships first)
Read-only queries over the architecture model:
- `simulate_refactor(operation, params) → FeasibilityReport` — checks whether the described operation would create an import cycle, change visibility contracts, or affect callers outside the module
- `list_refactor_operations(package) → Vec<AvailableOperation>` — what mechanical operations are available for a given package (complement to `list_refactor_candidates` which detects smells)
- No file writes; no build invocations

### Stage 2 — Go operation catalog v1 (#155)
Supported operations for Go packages:
- **MoveFiles**: move one or more `.go` files from package A to package B (new or existing), rewriting the `package` declaration and all import paths across the module
- **ExtractPackage**: split one Go package into two at the file level, with cycle pre-check before any write
- **RenamePackage**: rename a package's leaf identifier throughout the module
Non-goals: directory renames that cross module boundaries, cgo packages, generated file rewrites (those are regenerated by their generators).

### Stage 3 — MCP tools and architecture-checker integration (#156)
New MCP tools:
- `list_refactor_operations` (feasibility)
- `simulate_refactor` (what-if, read-only)
- `plan_refactor` → `RefactorPlan` (ordered edit list + verification steps)
- `apply_refactor(plan_id)` → `RefactorResult` (atomic apply + toolchain verify)
Architecture checker integration: `go-package-focus` findings attach an `available_operations` hint listing mechanical operations the engine can perform for that finding.

## Acceptance criteria

1. `simulate_refactor` returns a `FeasibilityReport` that includes at minimum: feasible (bool), blocking reasons (cycle detection, visibility breaks, external-module caller impact), and a list of files that would be touched.
2. `plan_refactor` for a MoveFiles operation produces a `RefactorPlan` with a deterministic, ordered edit list covering: (a) package-declaration rewrites in moved files, (b) import-path rewrites in all importers within the module, (c) test-package renames where the test package references the old package name.
3. `apply_refactor` is atomic: either all file writes complete, or the tree is left unchanged. A stale plan (any touched file modified since planning) is rejected with a clear error, not best-effort applied.
4. After a successful apply, the engine runs `go build ./...` and `go vet ./...` over the affected packages; if either fails, the apply rolls back and returns the tool output as the error.
5. Plans have a concurrency guard: the plan records which paths it touches, and `apply_refactor` refuses to proceed if any of those paths appear in another in-progress plan (file-level lock, not process-level).
6. The MCP tool `list_refactor_operations` returns an empty list (not an error) for packages where no mechanical operation is currently supported.
7. Build-tagged files (files with `//go:build` constraints), `*_test.go` files, generated files (files with the `// Code generated` marker), and files in `internal/` packages are each handled correctly: build-tagged and generated files are reported as a warning in the plan (not silently rewritten), test files are rewritten when their package name matches the moved package, and `internal/` visibility is enforced as a blocking feasibility constraint.
8. A backtest against the canonical corpus (`kubernetes/kubernetes`, `denoland/deno`, `BurntSushi/ripgrep`) runs without panics and produces zero false-positive "successful apply" results on packages that would actually fail `go build` after the move. (Dry-run mode required; applies against corpus do not happen in CI.)
9. All new MCP tools appear in the output of `kibitzer mcp list` and in the MCP server's tool-list response.
10. Unit tests cover: cycle creation (should block), visibility change (exported symbol moved to internal package, should block), stale-plan rejection, rollback on `go build` failure, and at least two successful end-to-end MoveFiles cases.

## Non-goals

- Deciding *whether* a split should happen (advisory evidence stays with `go-package-focus` and human review)
- Semantic refactorings that change observable behavior
- Cross-module or cross-repository changes
- Non-Go languages in this first iteration
- Integrating with `gopls`'s rename/move protocol (investigate first, fall back to direct AST edit if gopls does not expose package-level move programmatically)

## Key open questions

1. Does `gopls` expose a programmatic package-level move API, or must the engine implement import-path rewriting via direct tree-sitter AST edits? (Investigation required before Stage 2 design is final — see research.md.)
2. What is the right transaction primitive for multi-file atomic apply? (In-memory shadow tree vs. OS rename(2) vs. a temporary worktree branch.)
3. Should `RefactorPlan` be persisted to disk (for agent hand-off between turns) or held in-process only (simpler but loses state on restart)?
